02 — Enfoque y arquitectura

Sin frameworks de agentes, con contratos

El flujo es determinista (diseño → clase → evaluación → progresión) y el LLM es el motor de contenido, no un planificador: una orquestación propia resultó más simple, depurable y explicable que LangChain.

verified

Salida estructurada por contrato

Todo lo que el programa consume (perfil, temario, guiones, quizzes, la decisión de avanzar un paso) se pide como JSON con esquema explícito y se valida; si no valida, se reintenta con el error en el prompt.

calculate

Calificación local y determinista

El LLM genera preguntas, pero la nota es una comparación de índices en el servidor — nunca depende de una segunda llamada que pueda alucinar. Las respuestas correctas jamás viajan al navegador.

database

El diseño vive en una base de datos

Cada curso tiene su SQLite: diseño, guion por clase, perfil, progreso y chats. React + Mantine compilado y servido por el mismo FastAPI; carriles de modelo por tarea (potente para diseñar, liviano para conversar).

03 — Ingeniería de prompts

La pedagogía se especifica, no se asume

Antes de fijar los prompts investigamos literatura de enseñanza de la programación y tutores LLM. Tres hallazgos definieron el diseño:

La estructura pedagógica hay que especificarla. Las clases siguen un guion PRIMM generado primero (predicción antes de explicación, worked examples con subgoal labels, estado de variables línea a línea, error típico, reto). Separar el plan de la ejecución evita que la conversación divague.

Los LLM no conocen los errores reales de los principiantes. Inyectamos un banco de misconceptions documentadas (leer x = x + 1 como ecuación, while como interrupción instantánea…) y exigimos que cada distractor de quiz encarne una.

El avance también es una decisión con contrato. Cada turno devuelve {avanza, mensaje}: si el mensaje atiende el paso, avanza; si es un saludo o una duda, responde sin avanzar — un «hola» no dispara media lección. El conversatorio aplica los guardrails de Khanmigo (pistas, no soluciones) y los reintentos exigen variantes (patrón PrairieLearn).

04 — Cómo ejecutarlo

Cuatro comandos

Requisitos: Python ≥ 3.12, uv y una API key de OpenAI. No necesitas Node: el frontend React ya viene compilado y lo sirve el propio backend. 

git clone https://github.com/AndresGuido9820/trabajo2-agente-tutor
cd trabajo2-agente-tutor
uv sync                    # instala todas las dependencias
cp .env.example .env       # y pon tu OPENAI_API_KEY=sk-...
uv run tutor-web           # abre http://127.0.0.1:8017

Opcionales en .env: TUTOR_MODEL (default gpt-5-mini), TUTOR_MODEL_CHAT=gpt-5-nano (turnos más rápidos), TUTOR_IMAGENES=1 (ilustraciones con IA, bonus). Para desarrollo: uv run pytest (303 pruebas con dobles del LLM), ruff y mypy estricto.

05 — Desafíos y soluciones

Lo que se rompió y cómo se arregló

Timeouts disfrazados

Las generaciones largas superaban el timeout del SDK, que reporta el corte como error de conexión: el sistema reintentaba llamadas que iban bien. Solución: timeout de 180 s y respuesta-vacía tratada como transitoria (los modelos razonadores gastan tokens de razonamiento dentro del límite).

El front también necesita pruebas

Un bug de método HTTP pasó inadvertido porque los tests del API no ejercitan el JS. Añadimos bots Playwright que recorren la app real: capturas, E2E de caída-y-reintento del servidor y auditoría de accesibilidad con axe-core.

El system prompt manda

El examen diagnóstico jamás se generaba contra la API real: se pedía con el system del asesor, cuyo contrato JSON obliga a responder {mensaje, listo, perfil}. Los dobles de test no lo detectan — el humo real, sí. Cada salida estructurada necesita su propio system.

Probar sin gastar

Las 303 pruebas corren contra dobles del LLM inyectados (respuestas en cola, fallas simuladas del SDK); la API real solo se toca en scripts de humo y E2E manuales. CI corre formato, linter, mypy estricto, pytest y el build del frontend en cada push.

06 — Reflexión

Capacidades y limitaciones de los LLMs

Lo que sorprende

La transferencia de dominio: con solo «manejo bien Excel», el modelo produjo el mapa hoja→DataFrame, fórmula→expresión, tabla dinámica→agrupación en títulos, analogías y ejemplos de todo el curso. Y su capacidad de generar software pequeño: las demos interactivas salen funcionales y fieles al tema, verificadas por un control de calidad local.

Lo que hay que vigilar

La calidad pedagógica no emerge sola: sin el banco de misconceptions los distractores son triviales, y sin verificación exigida el modelo escribe preguntas con respuestas ambiguas con total confianza. El JSON se rompe bajo presión (seeds sin indentar, saltos sin escapar): todo lo estructurado necesita validación con reintento. Y el costo/latencia obligan a decisiones de producto: carriles de modelo, caches y streaming.
